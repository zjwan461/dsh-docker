# 字幕：原生渲染还是后期烧录

**一句话结论：H3 能"把字幕画进画面"，但不能给你一条字幕轨。所以"烧字幕"不是无脑操作，要先选路线。**

---

## 1. 先把事实分清楚

| 说法 | 对不对 | 准确表述 |
|---|---|---|
| "H3 支持生成字幕" | ✅ 但容易误解 | H3 能**把文字渲染进像素**，包括字幕、招牌、UI、品牌字 |
| "H3 会输出字幕文件" | ❌ | 没有任何视频模型输出可编辑的 `.srt` / `.ass` |
| "那我自己用 ffmpeg 烧" | ⚠️ 有前提 | 只有**素材里本来没有字**时才该烧 |

fal.ai 对 H3 的描述是三大强项之一：「渲染清晰可读的文字与界面」；官方示例里也直接写 "MiniMax H3 renders text, subtitles, brand assets, UI, game content, and product visuals"。

但另一边的实测结论是：**可编辑的字幕不会从视频模型里出来**。要能改、能翻译的字幕，只能拿成品音轨去转写（[apiyi 对比](https://help.apiyi.com/en/ai-generated-video-subtitles-model-vs-post-production-en.html)）。

**所以"H3 支持字幕"= 画在画面里，改一个字就要重新生成，换语言要重新生成。**

---

## 2. 更麻烦的是：H3 会自己加字幕

这不是"你要不要"的问题，是"它经常不请自来"：

- 社区常见抱怨：「这 minimax h3 出来的视频，老是带字幕怎么搞？」
- 韩语实测：用韩文对白，**经常自动烧上字幕**——因为训练数据里大量韩语视频自带字幕（[minimaxh3.co.kr](https://minimaxh3.co.kr/en/blog/minimax-h3-korean-video)）
- 官方提示词结构里**没有 subtitle 开关**，没有任何字段能关掉它

我们自己的实测也印证：写给二维动漫街景，明明没要文字，**招牌位置自己长出一片乱码**。

### 2.1 抑制字幕的三种手段（都不保证）

| 手段 | 做法 | 实测/社区反馈 |
|---|---|---|
| 正向占位 | 只描述画面里有什么（干净的墙、纯色背景、虚化光斑） | ⚠️ 有效但不彻底 |
| 显式否定 | `Screen: no subtitles, no on-screen text, no watermark.` | ⚠️ **有分歧**：韩语教程说这比"只说该有什么"更有效；HuggingFace 讨论区有人说 negative 对字幕完全无效 |
| 改景别 | 用中景代替近景 | ✅ 近景最容易把台词烧成字幕/印花，退到中景明显好 |
| **兜底** | 后期裁切、遮盖、局部重绘 | 唯一确定的手段 |

> **对 skill 的修正**：我原来写"不要写负面词"，这条对**画面内容**成立（cfg=1 没有负面分支），
> 但对**字幕**这个具体问题，社区有成功案例。**结论：字幕可以试一句显式否定，但不要指望它，必须准备兜底。**

### 2.2 三种"双字幕灾难"

1. **H3 自带 + 你烧的** → 两行字叠在一起
2. **部分镜头有字、部分没有** → 一集里观感断裂
3. **硬字幕 + 平台自动字幕** → 三行

---

## 3. 三条路线，怎么选

| 路线 | 产出形态 | 可编辑 | 可翻译 | 成本 | 适合 |
|---|---|---|---|---|---|
| **原生渲染** | 烧进像素 | ❌ 改字=重渲 | ❌ | 一次生成 | 风格化字卡、歌词排版、品牌字、UI 演示 |
| **后期烧录** | 烧进像素 | ✅ 改字幕重烧 10 秒 | ✅ 换语言重烧 | 几乎为零 | **对白字幕（默认走这条）** |
| **软字幕轨** | 独立轨 | ✅ | ✅ | 几乎为零 | 需要开关、B站/YouTube 上传、送审 |

### 决策树

```
这段文字是不是"画面设计的一部分"（字卡、歌词、招牌、UI）？
├─ 是 → 原生渲染（提示词里用双引号写死），接受改字要重渲
└─ 否（是对白字幕）
   ├─ 要翻译 / 要多平台 / 要能改 → 生成干净画面 + 后期烧录或软字幕
   └─ 只发一个平台、不再改 → 可以原生渲染，但先测 3 条看字形稳不稳
```

**默认：对白字幕走后期限烧；只有"字幕本身是设计元素"时才用原生。**

---

## 4. 什么时候原生渲染是对的

官方有一个专门的 skill 做这件事（`music-video-subtitle-generator`），它把 on-screen text 当**空间设计层**，不是字幕条。它的规则值得抄：

- 文字可以站在**前景/中景/背景**，可以被肩、手遮挡
- **不能遮眼睛和主要表情**；关键口型时避开嘴
- 有唱词时，**可见文字必须和唱出来的字逐字一致**
- **每个镜头只有一个主要文字事件**
- 文字要跟着节拍动：击碎、扫出、砸进来

这套东西用在 **MV 歌词排版、标题卡、漫画拟声字**上是对的；用在"两个人说话的字幕"上是错的。

---

## 5. 文字渲染的可靠性边界（决定你敢不敢用原生）

来自对 H3 文字能力的实测综述（[WaveSpeed](https://wavespeed.ai/blog/minimax-h3/minimax-h3-readable-text-in-video/)）：

| 内容 | 结果 |
|---|---|
| 短词、简单 logo 形状 | 有时能活 |
| 完整句子 | 通常崩：乱码、错字 |
| 精确产品名 | 崩，而且**逐帧闪动变形** |
| 品牌名烧错 | 比没有字更糟，而且事后修不掉 |

**判据：这段字如果错了，你能不能接受重渲一次？不能，就别用原生。**

尤其：**品牌名、产品名、数字、外文，一律后期叠。**

## 6. 交付前必做：三秒查底部

```bash
python qa.py EP01/out/final.mp4 --textcheck
```

会输出 `final_bottom.png`：整条片子底部 30% 抽 6 帧拼成 3×2。**看一眼就知道有没有已经烧进去的字。**

实测样例（这条是后期烧的字幕，横条里能清楚看到两句话）：

![底部横条示例](.h3check/demo/demo_sub_bottom.png)

> 为什么不做自动判断：字幕文字**逐句在变**，像素差测不出来；
> 我试过"底部比全画面更静止就算有字"的启发式，在同一素材的有/无字幕两版上给出**相同数值**，直接判错。
> **这种不可靠的检测不该写进交付流程**，所以改成出图给人看。

### 6.1 检查清单

- [ ] 每条素材跑一次 `--textcheck`，确认底部干净
- [ ] 如果已有字：**不要再叠**，要么裁掉，要么重生成
- [ ] 一集里所有镜头的"有没有字"必须一致
- [ ] 烧字幕前，先确认这一版是最终文案（改一次要重烧）

## 7. 落到本项目

| 场景 | 做法 |
|---|---|
| 漫剧对白 | 生成干净画面（中景优先）→ `finish.py --subs-from` 后期烧 |
| 科普对话 | 同上；数字和外文一定后期 |
| 漫画拟声字、章节卡、第 N 天 | **后期叠**（ASS 一层写全），不要让 H3 画 |
| MV 歌词排版 | 可以原生，但要接受重渲；或用官方 MV skill 的设计层写法 |
| 品牌/产品名 | 永远后期 |

`finish.py` 的行为：**只有显式给 `--ass` 或 `--subs-from` 才烧字幕**，不会默认叠。
如果同时给了字幕参数，它会在日志里提醒你先查底部横条。
